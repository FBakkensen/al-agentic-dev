# AL language server as a base plugin across platforms

Research for [FBakkensen/al-agentic-dev#23](https://github.com/FBakkensen/al-agentic-dev/issues/23).

## Question

SShadowS's AL LSP ships one plugin per platform (`al-language-server-go-windows`, `-go-linux`, `-go-darwin`, plus a deprecated cross-platform `al-language-server-python`) from the `al-lsp-for-agents` marketplace and needs `ENABLE_LSP_TOOL=1`. How can a single al-agentic-dev `plugin.json` `dependencies` entry require it on Windows, Linux (CI, cloud sessions), and macOS, and what does the plugin do when the variable is unset?

## 1. How each variant declares its LSP server, and whether Claude Code selects by OS

- Every `al-lsp-for-agents` plugin variant declares its server in a root `.lsp.json` file (Claude Code's default LSP location), not in an inline `lspServers` key in `plugin.json`. The plugin-root `plugin.json` in this repo carries only metadata (`name`, `version`, `description`, `author`, `repository`, `license`, `keywords`) — no `lspServers` key.
  - Windows (`al-language-server-go-windows/.lsp.json`, cloned repo, commit at research time):
    ```json
    {
      "al": {
        "command": "${CLAUDE_PLUGIN_ROOT}/bin/al-lsp-wrapper.exe",
        "args": ["--launcher", "claude-code"],
        "extensionToLanguage": { ".al": "al", ".dal": "al" },
        "transport": "stdio", "initializationOptions": {}, "settings": {}, "maxRestarts": 3
      }
    }
    ```
  - Linux (`al-language-server-go-linux/.lsp.json`): identical except `"command": "${CLAUDE_PLUGIN_ROOT}/bin/al-lsp-wrapper"` (no extension).
  - Both bundle the compiled binary at `${CLAUDE_PLUGIN_ROOT}/bin/al-lsp-wrapper[.exe]` inside the plugin itself — confirmed on disk locally: `~/.claude/plugins/cache/al-lsp-for-agents/al-language-server-go-windows/1.17.0/bin/al-lsp-wrapper.exe` and (from my own probe install, below) the Linux plugin's `bin/al-lsp-wrapper` is an `ELF 64-bit LSB executable, x86-64 ... statically linked, Go BuildID=...` (verified with `file`).
  - Live repo state (cloned `https://github.com/SShadowS/al-lsp-for-agents`, `main`, at research time): only two plugin folders are registered in `.claude-plugin/marketplace.json` — `al-language-server-go-windows` and `al-language-server-go-linux`. **There is no `al-language-server-go-darwin` plugin and no `al-language-server-python` plugin in the current marketplace, despite the ticket's premise and despite the repo's own `README.md` listing all four in its "Available Wrappers" table.**
    - The Python wrapper was deprecated and its plugin folder removed: `git log --oneline` on the cloned repo shows `6700e40 Bump version to 1.3.11, add Code Lens support, deprecate Python wrapper`; only `README.md` and `test-al-project/DEBUG.md` still mention `al-language-server-python`, and no such folder exists at HEAD.
    - Darwin has no build job and no shipped binary: `.github/workflows/release.yml`'s build matrix is `windows-latest`/`goos: windows` and `ubuntu-latest`/`goos: linux` only — no macOS entry. `al-language-server-go/README.md` (the shared Go source, not itself a marketplace plugin) documents a manual `GOOS=darwin GOARCH=amd64 go build ...` command, but nothing runs it in CI and no `al-language-server-go-darwin` folder exists in the repo. Darwin in the README table is aspirational, not shipped.
  - Sources: `.claude-plugin/marketplace.json`, `README.md`, `KnownIssues.md`, `.github/workflows/release.yml`, `al-language-server-go/README.md`, `git log --oneline` — all read from `https://github.com/SShadowS/al-lsp-for-agents` (cloned locally for this research, see probe log).

- **No Claude Code mechanism selects a plugin or an LSP command by OS.** Checked the full `plugin.json` fields table and the full marketplace-entry fields table — neither has an `os`/`platform` field or any conditional-source mechanism:
  - Plugin manifest reference: "The table lists the top-level keys in `plugin.json`. `name` is the only required key" — table has no platform field. [Plugin manifest reference](https://code.claude.com/docs/en/plugins-reference.md)
  - `lspServers` config fields (`command`, `extensionToLanguage`, `args`, `transport`, `env`, `initializationOptions`, `settings`, `workspaceFolder`, `startupTimeout`, `shutdownTimeout`, `restartOnCrash`, `maxRestarts`, `diagnostics`) — no platform field; `command` is "Language server binary. No spaces unless the value starts with `/`; put arguments in `args`" — a single hardcoded string, not something Claude Code branches on OS to fill in. [Same page, `lspServers` section]
  - The three variables Claude Code substitutes into LSP configs are exhaustively `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}` — no OS/platform variable. [Same page, "Environment variables" section]
  - [Marketplace reference](https://code.claude.com/docs/en/plugins/marketplace-reference.md) has no `os`/`platform` field either; the only OS-conditional behavior documented anywhere is unrelated to LSP selection: "Not on Windows: Claude Code refuses to install a link-mode plugin on Windows. Declare `"mode": "copy"` there," and a `command`-source install script runs "through `sh`, or through `cmd.exe` on Windows" (that's the plugin-fetch mechanism, not LSP server spawning).
  - **Contrast with Anthropic's own official code-intelligence plugins** (proof that OS-agnostic *is* achievable, just not the way al-lsp-for-agents does it): `gopls-lsp`'s marketplace entry (`https://github.com/anthropics/claude-plugins-official`, `.claude-plugin/marketplace.json`) declares:
    ```json
    { "name": "gopls-lsp", "source": "./plugins/gopls-lsp", "strict": false,
      "lspServers": { "gopls": { "command": "gopls", "extensionToLanguage": { ".go": "go" } } } }
    ```
    `command` is the **bare name `gopls`**, resolved from the user's own `PATH` — no `${CLAUDE_PLUGIN_ROOT}`, no bundled binary, one plugin entry for every OS. This works because the user installs `gopls` itself (a genuinely cross-platform Go tool) onto `PATH` per their own OS; the plugin never needs to know or branch on the OS. [Code intelligence plugins doc](https://code.claude.com/docs/en/plugins/code-intelligence.md) lists this as the standard pattern for every official language plugin (`clangd-lsp`, `pyright-lsp`, `rust-analyzer-lsp`, etc.). `al-lsp-for-agents` instead compiles and bundles its own `al-lsp-wrapper` binary inside each plugin at a fixed `${CLAUDE_PLUGIN_ROOT}/bin/...` path — that per-plugin bundling is *why* it needs a separate plugin per OS; it is a design choice in that repo, not a Claude Code limitation that a differently-built AL plugin couldn't avoid.

## 2. What happens when the wrong-OS plugin is installed, and whether a dependency on one variant is satisfied on another OS

Empirically tested in an isolated sandbox (`CLAUDE_CONFIG_DIR` pointed at a fresh scratch folder, never touching the real `~/.claude`), on this Windows 11 host, Claude Code CLI 2.1.283:

```
$ git -c core.longpaths=true clone --depth 1 https://github.com/SShadowS/al-lsp-for-agents.git <scratch>/repo
$ claude plugin marketplace add <scratch>/repo
✔ Successfully added marketplace: al-lsp-for-agents (declared in user settings)

$ claude plugin install al-language-server-go-windows@al-lsp-for-agents
✔ Successfully installed plugin: al-language-server-go-windows@al-lsp-for-agents (scope: user)

$ claude plugin install al-language-server-go-linux@al-lsp-for-agents
✔ Successfully installed plugin: al-language-server-go-linux@al-lsp-for-agents (scope: user)

$ claude plugin list
Installed plugins:
  ❯ al-language-server-go-linux@al-lsp-for-agents    Version: 1.17.0  Scope: user  Status: ✔ enabled
  ❯ al-language-server-go-windows@al-lsp-for-agents  Version: 1.17.0  Scope: user  Status: ✔ enabled

$ claude plugin details al-language-server-go-linux@al-lsp-for-agents
al-language-server-go-linux 1.17.0
Component inventory
  LSP servers (1)  al  (out-of-process tooling; no model context cost)
```

- **The Linux plugin installed and enabled without any error or warning on Windows**, and `claude plugin details` reports its LSP server (`al`) as registered exactly like the Windows plugin's. Claude Code performs no OS compatibility check at install, enable, or dependency-resolution time — consistent with there being no `os`/`platform` field anywhere in the schema (§1).
- The installed Linux plugin's bundled binary is a genuine Linux ELF executable (`file` on `.../al-language-server-go-linux/1.17.0/bin/al-lsp-wrapper` → `ELF 64-bit LSB executable, x86-64, ... statically linked, Go BuildID=...`), which cannot be spawned as a child process on Windows.
- What happens at *runtime* when Claude Code actually tries to start it (i.e., when editing a `.al`/`.dal` file triggers the LSP tool) is documented, not independently reproduced here (reproducing it needs an authenticated interactive session, which the isolated sandbox config doesn't have credentials for): "Missing binary: Claude Code starts `command` by name from the user's `PATH`. When the binary isn't there, the server fails to start and `claude --debug` logs `LSP server <name> failed to start`." [Plugin components — LSP servers](https://code.claude.com/docs/en/plugins/components.md#lsp-servers). Separately, the LSP tool itself "returns an error result for each LSP call on a file whose language server it can't start" [Tools reference, LSP tool behavior](https://code.claude.com/docs/en/tools-reference.md). A wrong-architecture binary (found on disk, but not a valid executable for the host OS) should hit the same "failed to start" path as a missing one — Claude Code doesn't distinguish "absent" from "present but not runnable here" in the docs' wording, and this project verified only that the binary is on disk and is Linux-only, not the exact runtime error text on Windows.
- **A `dependencies` entry naming one specific variant (e.g. `al-language-server-go-windows@al-lsp-for-agents`) is "satisfied" mechanically on every OS** — Claude Code installs/enables exactly that plugin regardless of host OS, per [Plugin dependencies](https://code.claude.com/docs/en/plugins/dependencies.md): a dependency entry is `"name"`, `"name@marketplace"`, or `{name, marketplace, version}`, and "Claude Code looks it up in the same marketplace as the declaring plugin unless you set `marketplace`" — nothing there is OS-aware either. So depending on the Windows variant would successfully install+enable that same Windows plugin on a Linux CI runner too; the dependency is satisfied, but the AL LSP itself would not function there (per the paragraph above).
- **Declaring both variants as two separate dependency entries does not give you "the right one per OS" either.** Both plugins register an LSP server named `al` for the same extensions (`.al`, `.dal`). Per the documented conflict rule: "Extension conflicts: when two enabled servers claim the same extension, the first registered handles those files and the other isn't used for them, whether the servers come from one plugin or two. The `/plugin` **Errors** tab shows the warning `LSP server "<name>" is not used for <ext> files`." [Plugin components — LSP servers](https://code.claude.com/docs/en/plugins/components.md#lsp-servers). Registration order is not documented as OS-aware, so enabling both variants together risks the wrong-OS one "winning" silently on any given host — this project did not determine the exact tie-break order (that would need an authenticated live session), so which one wins is `unverified:`, but the existence of the conflict, and that it isn't resolved by OS, is directly sourced from the doc quote above.

## 3. `ENABLE_LSP_TOOL`: still needed in 2.1.283? Can a plugin set it? What happens unset?

- The SShadowS README's Claude Code install steps say: set `ENABLE_LSP_TOOL=1` (session or permanent env var), add the marketplace, then `/plugin install`. [`README.md`, "Installation → Claude Code"]. `KnownIssues.md`/`BugReport.md` in the same repo reference `ENABLE_LSP_TOOL=1` as a precondition for reproducing an (already-resolved) `workspaceSymbol` bug, and confirm the fix landed by "Claude Code 2.1.x" / verified on "2.1.162" — i.e. this env var and the wrapper's docs predate, or were written around, an early/experimental phase of Claude Code's LSP tool.
- **`ENABLE_LSP_TOOL` does not appear anywhere in current Claude Code documentation.** Checked specifically:
  - [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence.md) — the current, full install flow for an LSP-backed plugin: install the language server binary, `/plugin install <plugin>@claude-plugins-official`, confirm the server starts by editing a file. No env var, no flag, anywhere in this flow.
  - [Tools reference — LSP tool behavior](https://code.claude.com/docs/en/tools-reference.md) — "Claude Code keeps the tool inactive until you install a code intelligence plugin for your language." Activation today is gated purely on **having an enabled plugin with an `.lsp.json`/`lspServers` for the file's extension**, not on any environment variable.
  - [Environment variables reference](https://code.claude.com/docs/en/env-vars.md) — no `ENABLE_LSP_TOOL` and no LSP-related variable of any name in the current canonical env-var list.
  - Corroborated by a web search of independent write-ups (not primary source, but consistent): `ENABLE_LSP_TOOL=1` shows up in older blog posts/GitHub issues describing the LSP tool as "new and still rough," from when it was gated behind that flag; none of the current code.claude.com pages mention it.
  - Empirically: installing `al-language-server-go-windows@al-lsp-for-agents` in the isolated sandbox (§2) — **without ever setting `ENABLE_LSP_TOOL`** — was enough for `claude plugin details` to report its LSP server as registered (`LSP servers (1) al`). Registration is not gated by the variable, at least at install/enable time.
  - **What I could not verify**: whether the LSP *tool actually activates end-to-end* (a live edit of an `.al` file triggering diagnostics/the `LSP` tool) also works with zero env vars in 2.1.283 — reproducing that needs an authenticated interactive session, and the isolated sandbox config has no credentials (`claude -p ... ` there returned `Not logged in`, and logging in would mean touching real credentials, which this task's isolation rule forbids). `unverified: full runtime activation without ENABLE_LSP_TOOL`, though every documentary and install-time signal points the same way — the flag is very likely vestigial for 2.1.283, carried over in SShadowS's README from an earlier Claude Code release.
  - **Can a plugin set it itself?** No first-party mechanism does this. The `plugin.json` `settings` key only takes effect for `agent` and `subagentStatusLine` — "other keys are dropped at load" [Plugin manifest reference — `settings`](https://code.claude.com/docs/en/plugins-reference.md#settings). `userConfig` values substitute into MCP/LSP server configs and Markdown content via `${user_config.KEY}`, and export as `CLAUDE_PLUGIN_OPTION_<KEY>` only to *hook* processes — not to the main Claude Code process's own environment, and not to a variable named by the plugin author (`ENABLE_LSP_TOOL` specifically) [same page, "Reference a saved value"]. So even if the variable still mattered, a plugin cannot set it for the session that's running it; only the user's own shell/settings can. This is moot if §3's main finding holds — current Claude Code doesn't read it at all.
- **What happens when it's unset**: per current docs, nothing special — the LSP tool is inactive only when no code-intelligence plugin is installed/enabled for the file's language, unrelated to this variable. Setting it is (at worst) a harmless no-op on 2.1.283.

## 4. Realistic options for al-agentic-dev

No option makes one `dependencies` entry work correctly on Windows, Linux, and macOS at once — Claude Code's plugin/dependency schema has no OS-conditional field anywhere (§1), and enabling several OS variants together collides on the same LSP server name rather than selecting between them (§2).

| Option | What it does | Consequence |
| :-- | :-- | :-- |
| **A. Depend on `al-language-server-go-windows@al-lsp-for-agents` only** | One `dependencies` entry, the Windows plugin | Works for Naveksa's Windows dev machines (the actual interactive users of AL LSP). Installs+enables on Linux CI too, but the bundled binary can't execute there — LSP calls there error rather than crash (§2). Moot for Claude Code cloud sessions specifically: "In cloud sessions, Claude Code doesn't start plugin language servers, so Claude gets no diagnostics or code navigation there" [Code intelligence plugins](https://code.claude.com/docs/en/plugins/code-intelligence.md) — that is a blanket rule independent of which OS variant is named, so no dependency choice buys AL LSP in a true cloud session. Note the ticket's "Linux (CI, cloud sessions)" bundles two different things: CI on an `ubuntu-latest` runner is a normal (headless) terminal session on Linux, where a Linux-native LSP plugin *would* actually start; Anthropic's own "cloud session" product (claude.ai/code, `--cloud`, mobile, routines — an isolated Anthropic-managed VM) is the one place LSP plugins never start at all, on any OS [Use Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web.md). |
| **B. No LSP dependency entry; document per-OS manual install** | Skip the `al-lsp-for-agents` entry in `dependencies`; tell developers to `/plugin install` their own OS's variant | Simple, no false confidence. Conflicts with ADR 0002 as described (which already decided to declare the AL LSP as a dependency) — listed for completeness, not as a live alternative to that decision. |
| **C. Depend on multiple variants at once** | Two or three `dependencies` entries, one per OS | Does **not** solve the problem: every variant registers the same LSP server name `al` for the same extensions, so only the first-registered one is used on any given host, and registration order is not OS-aware (§2) — the wrong-OS plugin can silently "win" while the right one sits enabled and unused. Not recommended. |
| **D. Ask SShadowS for a single cross-platform entry, modeled on Anthropic's own official LSP plugins** | File an upstream request/PR to stop bundling the compiled `al-lsp-wrapper` binary inside `${CLAUDE_PLUGIN_ROOT}`, and instead have users install one OS-appropriate `al-lsp-wrapper` build onto their own `PATH` (like `gopls`, `pyright-langserver`, etc.), so a single `.lsp.json`/marketplace entry can say `"command": "al-lsp-wrapper"` and work unchanged on every OS — exactly how `gopls-lsp`'s marketplace entry does it today (§1). This is the only option that produces one dependency entry that's actually correct everywhere, but it requires an upstream change al-agentic-dev doesn't control and has no timeline for. |
| **E. Ship our own wrapper plugin** | al-agentic-dev builds/bundles its own AL LSP plugin | Hits the identical wall as SShadowS's design (§1) unless built the "bare `PATH`-command" way of option D — otherwise it's the same per-OS-binary problem moved in-house, for more maintenance and no more correctness. |

**Recommendation:** **Option A** — depend on `al-language-server-go-windows@al-lsp-for-agents` only, since Naveksa's developers who interactively benefit from AL LSP are on Windows, and cloud sessions get no AL LSP regardless of which variant is named. Pair it with a short note (in the same doc that carries ADR 0002, or a follow-up issue) that CI/Linux gets no functional AL LSP from this dependency today, and that Option D is the durable fix if SShadowS is open to it.
