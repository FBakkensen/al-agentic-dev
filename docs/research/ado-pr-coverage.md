# Azure DevOps MCP coverage for Azure Repos pull requests

Research for [#10](https://github.com/FBakkensen/al-agentic-dev/issues/10). Question: what can the Azure DevOps MCP server (`microsoft/azure-devops-mcp`, npm `@azure-devops/mcp`) do for Azure Repos pull requests, and where does `az` (the `azure-devops` extension) have to take over? Scope: every operation that `skills/al-pull-request/SKILL.md` and `skills/al-pr-shepherd/SKILL.md` perform today with `gh`.

Researched 2026-09-27 against `microsoft/azure-devops-mcp` at [`4f9342f`](https://github.com/microsoft/azure-devops-mcp/tree/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c) (package version 2.10.0), the Microsoft Learn `az repos` / `az pipelines` references, and the Azure DevOps REST 7.1 reference. The `mcp__ado__*` tool schemas loaded in this Claude Code session were used as extra evidence. Nothing was created or changed in Azure DevOps.

## Bottom line

- The MCP `repositories` domain covers the PR lifecycle end to end, except for two gaps. It can create, update, publish a draft, add reviewers, vote, list/create/reply to threads and resolve them, and arm auto-complete with a merge strategy.
- **Gap 1: policy evaluations.** No MCP tool reads branch-policy evaluation status, which is Azure Repos' equivalent of "required checks". `az repos pr policy list --id <n>` is the direct replacement for `gh pr checks`.
- **Gap 2: immediate completion.** MCP `update` accepts only `Active|Abandoned`. Completing a PR goes through auto-complete, or through `az repos pr update --status completed`.
- Build results for diagnosis (status, logs) are MCP `pipelines` tools, but that domain is **not enabled** in this session's `ado` server.
- Neither tool has a watch mode, so `/al-pr-shepherd` needs its own poll loop.

## Domains and auth

**Local server** (`npx -y @azure-devops/mcp <org>`):

- Domains are chosen with `-d` / `--domains`; the default is `all`. Names: `core`, `work`, `work-items`, `search`, `test-plans`, `repositories`, `wiki`, `pipelines`, `advanced-security` ([src/index.ts L39–41](https://github.com/microsoft/azure-devops-mcp/blob/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c/src/index.ts#L39-L41); [GETTINGSTARTED.md](https://github.com/microsoft/azure-devops-mcp/blob/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c/docs/GETTINGSTARTED.md)).
- The two PR skills need **`core repositories work-items pipelines`**. `core` is needed for `core_get_identity_ids`. `pipelines` is the one missing from this session's server, which currently exposes `core`, `repositories`, `work-items`, `work` and `search` tools.
- Auth is `-a` / `--authentication`, choices **`interactive` (default) | `azcli` | `env` | `envvar` | `pat`**, all lowercase ([src/index.ts L46–50](https://github.com/microsoft/azure-devops-mcp/blob/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c/src/index.ts#L46-L50)).
  - `env` uses `DefaultAzureCredential`.
  - `envvar` reads a bearer token from `ADO_MCP_AUTH_TOKEN`.
  - `pat` reads `PERSONAL_ACCESS_TOKEN`, which holds base64 of `<email>:<pat>` ([GETTINGSTARTED.md](https://github.com/microsoft/azure-devops-mcp/blob/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c/docs/GETTINGSTARTED.md)).
- Default project and team can be set with `ado_mcp_project` / `ado_mcp_team` ([README](https://github.com/microsoft/azure-devops-mcp/blob/4f9342fba14614a5c6615e3f93bea79ef2c7fc3c/README.md)).

**Remote server** (`https://mcp.dev.azure.com/{org}`, which Microsoft recommends) ([Learn: remote MCP server](https://learn.microsoft.com/en-us/azure/devops/mcp-server/remote-mcp-server)):

- Toolsets are chosen with the `X-MCP-Toolsets` header, and the names differ from the local ones: `repos`, `wit`, `pipelines`, `work`, `wiki`, `testplan`, `advsec`, `elm`. `X-MCP-Readonly: true` restricts the server to read-only tools.
- The remote tool list adds `repo_pull_request` `get_changes`, which the local TOOLSET.md does not list. Its `repo_pull_request_thread_write` lists no `update` action.
- Auth is Microsoft Entra OAuth only, on an Entra-backed organization. **Claude Code needs a custom Entra app registration**: redirect `http://localhost:3118/callback`, delegated permissions on the "Azure DevOps MCP" enterprise app `2a72489c-aab2-4b65-b93a-a91edccf33b8`, and admin consent. It is then configured with `claude mcp add --transport http ado https://mcp.dev.azure.com/{org} --client-id <id> --callback-port 3118`, or with a `.mcp.json` `oauth` block.
- Granting a toolset does not grant permissions. OAuth scopes and the user's Azure DevOps permissions both have to allow an operation.

**`az` CLI** ([Sign in with a PAT](https://learn.microsoft.com/en-us/azure/devops/cli/log-in-via-pat?view=azure-devops)):

- `az devops` commands accept an `az login` (Entra) session, `az devops login` with a PAT, or `AZURE_DEVOPS_EXT_PAT`.
- Starting the local MCP with **`--authentication azcli`** means one `az login` serves both the MCP server and the `az repos pr policy` fallback.

## Implications for the skill rewrite (for #14; not decided here)

- `/al-pull-request`:
  - `repo_pull_request` `list` → `create` (`isDraft: false`, `workItems`) or `update`.
  - Drop the `AB#<id>` body line in favour of `workItemRefs`.
  - For an existing PR, add missing links with `wit_work_item_link_write` `link_to_pull_request`.
  - Keep the body under 4000 characters.
- `/al-pr-shepherd`:
  - Replace `gh pr checks --watch` with a PowerShell poll over `az repos pr policy list`.
  - Read threads through MCP with `fullResponse: true`.
  - Diagnose builds through MCP `pipelines_*`.
  - Merge on the user's go with MCP `update` `autoComplete` + `mergeStrategy: NoFastForward`, which preserves the no-rebase rule. The alternative is `az repos pr update --status completed`.
  - The Copilot-reviewer branch needs a separate decision.
