# al-visualize — the decision surface

One self-contained HTML page per decision moment, generated by you directly — no renderer, no build step. [SURFACE.md](SURFACE.md) is the page contract: layout, palette, navigation, and the card anatomy. The surface presents; chat is the only answer channel. Ask every question in the reply itself, as plain text — never through a question or elicitation tool.

## Choose the notation

Match the decision to a notation the reader already holds — the standard picture is also the densest instruction a later agent can consume:

- structure and seams → C4 component map
- workflow across actors → event-model swimlanes (commands → events → read models)
- object lifecycle → state machine, guards and owning procedures on the edges
- interaction order and transaction boundaries → sequence diagram
- data shape → ERD
- user flow → journey map with friction markers
- delivery order → slice and task dependency graph
- a landed change → component diff (added / modified / unchanged context) with triaged risks

Nothing on the menu fits → compose an ad-hoc visual, and the page's first card names which notations were considered and why each fails this decision.

## Ground every node

Every BC object, table, field, procedure, event, enum value, or file a node names is confirmed by a lookup in the current session, never recalled. A claim about code names the object and procedure behind it. A node nobody can trace to something real is decoration and gets cut.

The page's content splits three ways: locked context — what is already agreed; open decisions — the questions the caller sent, each with lettered options and one recommendation marked; evidence — scope, risks, the diagram itself.

## Present and settle

Write the page to disk and open it in the browser through whatever browser capability the harness offers; without one, give the user the path to open themselves. Then interview the open decisions in chat, one question per message, each naming its card's stable ID and its lettered options. As each answer lands, update the page — the open card becomes a locked card carrying the pick — and reload it, so the user answers every remaining question with the current truth in view and the page closes as the approved picture.

## Persist or discard

A design-time surface the user approved is saved as `specs/<branch>/visuals/<topic>.html` and committed with a plain descriptive message, so a later session can read the HTML source as the approved picture and reopen it on demand. A review-side surface — a change diff, a quiz anchor — is a session artifact and leaves nothing behind.

## Close

Report the settled decisions and anything left open back into the flow that invoked the surface; the caller owns what happens next, and any task state it implies is the caller's outcome to hand to `/al-routing`. Invoked directly by the user, close naming what the surface settled, then `/al-next`.
